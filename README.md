## Подготовка среды

Если среда для части А уже установлена, выполните только шаги 5-7.

### Вариант А. Свой ноутбук (рекомендуется): macOS, Linux или Windows через WSL2

1. **Windows:** установите WSL2 (PowerShell от имени администратора: `wsl --install`, перезагрузка, Ubuntu). Все дальнейшие команды выполняйте в терминале Ubuntu, репозиторий храните в домашнем каталоге WSL (`~`).
2. **git, make, curl:** macOS - `xcode-select --install`; Ubuntu / WSL - `sudo apt update && sudo apt install -y git make curl`.
3. **uv:** `curl -LsSf https://astral.sh/uv/install.sh | sh` (macOS также `brew install uv`). Python 3.12 uv скачает сам.
4. **Foundry v1.8.5:** `curl -fsSL https://foundry.paradigm.xyz | bash`, откройте **новый** терминал, затем `foundryup -i v1.8.5`.
5. **Репозиторий:** на странице шаблона на GitHub - **Use this template - Create a new repository**, затем:
   ```bash
   git clone https://github.com/<ваш-логин>/<имя-репозитория>.git
   cd <имя-репозитория>
   ```
6. **Установка и проверка:**
   ```bash
   make setup
   make check
   ```
   `make check` проверяет uv, Python, git, forge, anvil, web3, компиляцию и один полный прогон сценария (около 10 секунд) и создаёт `check-result-pz2.txt`. В конце должно быть `ИТОГ: ГОТОВО`.
7. **Сохраните `check-result-pz2.txt`: он загружается в форму сдачи вместе с отчётом.**

## Задание

`src/Vault.sol` - хранилище ETH. Участники вносят и выводят ETH; оператор может выводить средства на обслуживание (`sweep`); guardian может поставить хранилище на паузу. **Контракт содержит две уязвимости**, они уже эксплуатируются. Код контракта не меняется: задача - обнаружить атаки по данным блокчейна и оценить правила обнаружения.

`make run` поднимает локальный блокчейн anvil, разворачивает контракты и проигрывает сценарий:

- **легитимный трафик** - 250 транзакций: депозиты, выводы, переводы, пакетные выплаты `Payroll` (несколько выводов в одной транзакции), плановая смена оператора владельцем;
- **инциденты A1 и A2** - атака повторного входа (reentrancy) на `withdrawAll`: депозит и многократный вывод в одной транзакции (`src/Attacker.sol`);
- **инцидент B** - захват роли оператора через `setOperator` без проверки владельца; через несколько блоков - вывод средств через `sweep`.

После каждой транзакции монитор (`detect/monitor.py`) читает новый блок, разбирает события Vault и применяет правила из `detect/rules.py`. В конце `detect/evaluate.py` сравнивает тревоги с разметкой сценария и печатает метрики. Монитор разметку не видит.

### Правила

| Правило | Что обнаруживает | Состояние |
|---|---|---|
| R1 | повторный вход: несколько выводов в одной транзакции | работает, но много ложных тревог - **уточнить** |
| R2 | платёжеспособность: ETH в хранилище меньше суммы балансов участников | готово, пример |
| R3 | захват роли оператора: сменил не владелец или новый оператор вне списка разрешённых | заготовка - **написать** |

Правило - функция `(tx, ctx)`, которая возвращает текст тревоги или `None`. Описание полей `tx` и `ctx` - в начале `detect/rules.py`. **Меняйте только `detect/rules.py`.**

### Порядок выполнения

1. **Б1.** Подготовьте среду (раздел выше), сохраните `check-result-pz2.txt`. `make run`: запишите метрики R1-R3 до изменений.
2. **Б2.** Уточните R1: пакетные выплаты `Payroll` не должны давать тревог, инциденты A1 и A2 должны обнаруживаться. Проверка на другом легитимном трафике: `uv run python -m detect run --seed 7`.
3. **Б3.** Напишите R3 по TODO: роль оператора сменил не владелец или новый оператор вне списка разрешённых. Тревога должна предшествовать первому выводу средств.
4. **Б4.** `make run-respond` и `uv run python -m detect run --respond R1`: сравните потери и число отклонённых легитимных транзакций. Сколько ложных пауз в сутки даст каждое правило при 100 000 транзакций? Какой уровень реагирования подходит каждому правилу: оповещение, пауза, ограничение вывода?
5. **Б5.** Мини-проект практической работы № 6 выполнен 30 раз без отказов. Рассчитайте верхнюю 95-процентную границу вероятности отказа по правилу трёх (3/n) и по Клопперу-Пирсону (1 - 0,05^(1/n)); сколько выполнений без отказов нужно для границы 1 %? Почему p95 по 30 наблюдениям неустойчив и сколько наблюдений нужно для верхней доверительной границы p95?
6. **Б6.** Опишите R1 и R3 по структуре Alerting and Detection Strategy; предложите правило межмодульной аномалии для своего мини-проекта: признак, порог, метрики проверки.

### Как читать отчёт

```
Транзакций: 256 (легитимных 250, атакующих 6), блоки 4-259
Инциденты: A1 - повторный вход, блок ...; A2 - ...; B - захват роли оператора, блок ...

Журнал тревог (блок, правило, разметка, сообщение):
  блок   34  R1   ЛОЖНАЯ (payroll)       3 событий Withdrawal в одной транзакции
  ...

Правило                                 Тревог   TP   FP Precision     FPR  Инциденты: задержка/запас, блоков
R1  Повторные выводы в одной транзакции   ...
```

- **TP / FP** - тревоги на атакующих / легитимных транзакциях.
- **Precision** - доля тревог, которые оказались атаками: TP / (TP + FP).
- **FPR** - доля легитимных транзакций, на которых правило подняло тревогу: FP / число легитимных.
- **Инциденты** - сколько из трёх инцидентов правило обнаружило (полнота по инцидентам).
- **Задержка** - блоков от начала инцидента до первой тревоги. **Запас** - блоков от первой тревоги до первого ущерба: сколько времени есть на реакцию. 1 блок Ethereum = 12 с.
- **Потери** - сколько ETH ушло из хранилища в атакующих транзакциях.

### Реагирование

`make run-respond` - то же, но guardian ставит хранилище на паузу по первой тревоге R3. Другие правила: `uv run python -m detect run --respond R1` (или `R1,R3`). После паузы все транзакции отклоняются, в том числе легитимные - отчёт показывает, сколько.
